# intent-check

CRS-05 최종 확인 단계에서 staging 화면을 기획 의도와 대조합니다.
차이 목록(항목 · 기대 · 실제 · 근거)과 확인하지 못한 항목을 나눠서 냅니다.
조회와 화면 이동만 합니다. 저장 · 삭제 · 발송 · 결제 같은 쓰기 동작은 하지 않습니다.
차이가 버그인지 의도 변경인지는 기획자가 판단합니다.

## 어디서 되는가

화면 판별은 `references/_shared/surfaces.md`를 따릅니다.

| 화면 | 브라우저 | 로그인 | 안 될 때 |
|---|---|---|---|
| Chat | 없음 | — | "브라우저가 필요해 Cowork나 Code 탭에서 해 주세요"라고 알리고 멈춥니다 |
| Cowork | 내장 브라우저 | 사용자가 내장 브라우저 창에서 직접 로그인하고 알려 줍니다 | staging은 WireGuard(VPN)가 켜진 PC에서만 열립니다. 안 열리면 그렇게 알리고 Code 탭을 권합니다 |
| Code 탭 | Claude in Chrome 확장. 새 탭을 만들어 쓰고, 사용자가 쓰던 탭은 건드리지 않습니다 | Chrome에 이미 로그인돼 있으면 그대로 씁니다. 아니면 직접 로그인을 요청합니다 | 확장이 없으면 설치하라고 안내하고 멈춥니다. staging이 안 열리면 WireGuard가 켜져 있는지 확인해 달라고 합니다 |

## 하지 않는 것

- 쓰기 동작. 허용 · 금지 동작은 `references/safety.md`를 브라우저를 열기 전에 읽고 그대로 따릅니다.
- 허용 목록 밖의 주소 열기. 운영 주소에서는 사용자가 요청해도 실행하지 않습니다.
- 로그인 · 비밀번호 다루기. 비밀번호 입력란에는 아무것도 입력하지 않고, 계정 정보를 묻거나 적지 않습니다.
- 화면 · 코드 · 데이터 고치기.
- "확정", "통과", "문제없습니다"라고 쓰기.

## 진행 순서

### 1. 화면 판별

Chat이면 위 표대로 알리고 멈춥니다.

### 2. 주소 검사

- `references/hosts.md`를 읽습니다.
- 허용 목록이 비어 있으면 "허용된 staging 주소가 아직 정해지지 않아 실행하지 않습니다. 리드에게 문의해 주세요."라고 알리고 멈춥니다.
- 받은 주소의 호스트가 허용 목록의 호스트나 모양에 맞을 때만 진행합니다. 차단 목록에 있거나, 어느 목록에도 없으면 멈춥니다.
- 주소를 받지 못했으면 묻습니다. 허용 목록의 주소를 보여 주며 고르게 할 수 있습니다.

### 3. 의도를 확인 단위로 쪼개기

확인 단위 하나는 한 화면 상태에서 캡처 한 장으로 판정할 수 있는 것입니다.

| 칸 | 내용 |
|---|---|
| 단위 | 원 항목 ID에 a · b를 붙입니다 (`REQ-03-a`). ID가 없으면 원문 인용과 위치를 씁니다 |
| 화면 | 주소와 도달 경로 (메뉴 › 탭) |
| 도달 동작 | 조회 · 이동만 (`references/safety.md`의 허용 동작) |
| 볼 것 | 요소와 축 (있음 · 문구 · 값 · 조건 · 예외 · 흐름) |
| 기대 | 원문 그대로 인용 |

- 조건 분기가 있는 항목("A면 X, B면 Y")은 조건마다 단위를 나눕니다.
- 그 조건을 만들려면 데이터를 바꿔야 하면 "확인 못 함 (쓰기 필요)"로 둡니다. 이미 그 상태인 데이터가 있으면 조회로 찾아 확인합니다.
- 쓰기 결과에 대한 항목("저장하면 토스트", "발송하면 상태 변경")은 "확인 못 함 (쓰기 필요)"입니다.
- 판정 기준이 없는 항목("눈에 잘 띄게", "편하게")은 "확인 못 함 (판정 기준 없음)"입니다.
- 필터 · 정렬 · 검색 · 탭 전환 · 모달 열기 · 페이지 이동으로 되는 항목은 확인합니다.

### 4. 확인 계획을 보여 주고 승인받기

브라우저를 열기 전에 아래를 보여 주고 승인을 기다립니다.

- 열 주소 목록 (모두 허용 목록 안)
- 확인 단위 목록: 단위 · 화면 · 도달 동작 · 볼 것
- 미리 "확인 못 함"으로 둔 항목과 이유
- 안내: "staging은 팀이 함께 쓰는 시험 데이터라 쓰기 동작은 하지 않습니다."

승인 없이 브라우저를 열지 않습니다.
사용자가 계획을 고치면 고친 계획을 다시 보여 주고 승인받습니다.

### 5. 브라우저 열기와 로그인

- 위 표의 화면별 경로로 엽니다.
- 로그인 화면이 나오면 "직접 로그인하신 뒤 알려 주세요"라고 하고 기다립니다.

### 6. 단위마다 확인

1. 허용 동작으로 화면에 도달합니다.
2. 이동할 때마다 현재 주소의 호스트를 봅니다. 허용 목록 밖이면 바로 멈추고 알립니다.
3. 캡처를 남기고 번호를 붙입니다 (캡처 1, 캡처 2 …).
4. 본 것을 적습니다: 요소의 문구는 화면 그대로 인용합니다.
5. Code 탭에서는 클릭마다 네트워크 요청을 봅니다. GET이 아닌 요청이 생기면 그 자리에서 멈춥니다 (`references/safety.md` 4절).
6. 계획에 없던 동작이 필요해지면 하지 않고 "확인 못 함"으로 둡니다.

### 7. 출력

- 대화 본문에 마크다운으로 냅니다. 양식은 `references/output.md`를 출력 직전에 읽고 따릅니다.
- 차이마다 근거 캡처 번호 · 주소 · 도달 경로를 붙입니다. 캡처가 없는 차이는 "차이"에 넣지 않고 "확인 못 함"으로 옮깁니다.
- 파일로 남겨 달라고 하면 그때 저장합니다. 위치는 argument로 받고, 없으면 Cowork 연결 폴더나 Code 탭 현재 폴더, 그것도 없으면 묻습니다.
- 글은 `references/_shared/writing.md`를 따릅니다.

## 한계

- 서비스에 조회만 되는 권한이 없어, 어떤 계정으로 로그인해도 쓰기를 막는 장치는 이 스킬의 규칙뿐입니다. 에이전트가 지키는 규칙이라 완벽하지 않습니다.
- Code 탭의 네트워크 감시는 사후 감지입니다. 이미 나간 요청은 되돌리지 못합니다.
- Cowork에서는 네트워크 요청을 볼 수 없을 수 있습니다. 그때는 허용 · 금지 동작 규칙만으로 진행한다고 계획 단계에서 알립니다.

## 이어지는 스킬

- 넘기기 전 글과 아티팩트 대조는 `handoff-check`가 맡습니다.
- 차이를 Figma 시안으로 정리하려면 `screen-to-hifi`를 쓸 수 있다고 알립니다.
