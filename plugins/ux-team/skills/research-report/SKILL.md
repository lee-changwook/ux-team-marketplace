# 리서치 리포트

학원 사용자 인터뷰 · 설문 · 현장 테스트의 응답을 리포트로 만든다.
자료 모양에 따라 **비교형**과 **단일형** 중 하나를 고른다(0절).
두 판본 모두 응답자 · 팀 · 전사에 그대로 보낼 수 있는 문서다.

## 어디서 되는가

화면 판별은 `references/_shared/surfaces.md`를 따른다. 안 되는 단계는 건너뛰지 말고 알린다.

| 단계 | Chat | Cowork | Code 탭 |
|---|---|---|---|
| 자료 읽기 (올린 파일 · CSV · md) | 됨 | 됨 (연결 폴더) | 됨 |
| 구글 폼 응답 화면 직접 읽기 | 안 됨. CSV를 달라고 한다 | 내장 브라우저, 로그인은 사용자 | Chrome 확장이 있을 때, 로그인은 사용자 |
| HTML 만들기 (`md_to_qs` · `assemble` · `check_shared`) | 됨 | 됨 | 됨 |
| 캡처 검증 (`shot.py`) | 안 됨 | 안 됨 | Chrome이 있을 때 고를 수 있음 |
| PDF (`to_pdf.py`) | 실행 환경에 브라우저 · 한글 글꼴이 있을 때만 | 같음 | Chrome이 있을 때 |
| 저장 | 내려받기 | 연결 폴더 | 저장 폴더 또는 현재 폴더 |

## 판본

| 판본 | 언제 | 뼈대 | 파일 |
|---|---|---|---|
| 비교형 | 응답 세트 둘이 같은 질문에 답함 | `templates/shared.html` | `<제목>.html` |
| 단일형 | 응답 세트 하나, 또는 섹션마다 질문이 다른 질문 리스트 | `templates/single.html` | `<제목>.html` |

- **응답 세트**: 같은 질문 리스트에 따로 답한 한 묶음. 한 학원에서 원장님과 실장님을 함께 인터뷰해 메모가 하나면 응답 세트는 하나다.
- **저장 위치**: argument로 받은 폴더. 없으면 Cowork 연결 폴더나 Code 탭 현재 폴더, 그것도 없으면 묻는다. Chat에서는 만든 파일을 내려받게 준다. 그 아래에 `<제목>/` 폴더를 만든다.
- **예시**: 처음 쓰거나 판단이 애매하면 `references/examples/`의 가상 예시를 읽고 따라 한다. 구조 · 문장 톤의 기준이다. 무엇을 보여 주는지는 `references/examples/README.md`.
- **스크립트 경로**: 아래 명령의 `$SKILL`은 이 SKILL.md가 있는 폴더다.

## 0. 시작 전에 정할 것

**판본.** 사용자가 "비교형으로" 또는 "단일형으로"라고 했으면 그대로 따른다. 말하지 않았으면 자료 모양으로 고른다. 대상이 몇 개인지가 아니라 **같은 질문에 양쪽이 답했는지**로 가른다.

1. 문항과 답을 QS로 옮기면서 양쪽 답이 모두 있는 문항의 비율을 센다. markdown은 `scripts/md_to_qs.py`가 세어 준다. 폼 · CSV는 QS를 만든 스크립트에서 두 응답 세트의 키가 모두 있는 문항을 센다
2. 비율로 고른다
   - 70% 이상이고 응답 세트가 정확히 둘: **비교형**
   - 30% 이하, 또는 자료가 한 곳의 인터뷰 · 질문 리스트 하나: **단일형**. 관찰 대상이 둘(예: 지금 쓰는 방식과 새 화면)이어도 섹션마다 질문이 다르면 단일형이다
   - 그 사이: 추천안과 비율을 함께 보여 주고 묻는다
3. 쓰기 전에 고른 판본을 한 줄로 알린다. 예: "단일형으로 만듭니다. 양쪽 답이 모두 있는 문항은 43개 중 2개입니다." 여기서 사용자가 바로잡을 수 있게 한다

**응답 세트가 셋 이상이면** 한 문서로 만들지 않는다. 이 스킬의 판본은 응답 세트 둘까지만 나란히 놓을 수 있다. 이유를 알리고 두 길 중에서 고르게 한다.
- 응답 세트마다 단일형을 하나씩 만든다
- 두 세트를 골라 비교형으로 만든다

예: "응답이 5곳에서 왔습니다. 이 스킬은 두 곳까지만 나란히 놓을 수 있습니다. 학원마다 단일형을 하나씩 만들까요, 두 곳을 골라 비교형으로 만들까요?"
응답을 집계하거나(`주 1회 4곳`) 여러 응답을 한 칸에 이어 붙이지 않는다. 원문 보존이 깨진다.

**서로의 답을 봐도 되는 사이인지.** 서로 다른 학원 · 소속의 응답 세트 둘 이상이 한 문서에 함께 보이면, 한 곳의 사정이 다른 곳에 그대로 보인다. 그 문서를 응답자에게도 보낼 때는 만들기 전에 "응답자들이 서로의 답을 봐도 된다고 동의했는지" 묻는다. 비교형도, 응답 세트 둘을 담은 단일형도 같다. 동의가 없으면 응답자에게 보낼 문서는 만들지 않고, 팀 안에서만 볼 문서로 만들지 묻는다.

**모르면 묻는다.** 제목, 누구에게 공유하는지(응답자 / 팀 / 전사), 출력 형식(HTML만 / PDF도). 요청이나 argument에 이미 있으면 묻지 않는다. 제목이 `.pdf`로 끝나거나 argument에 `pdf`가 있으면 PDF 요청으로 본다.

## 1. 자료 읽기

받는 자료: 구글 폼 응답, 회의록 · 녹음 요약, markdown 문서(문항지 · 질문 리스트 · 인터뷰 메모), CSV · 스프레드시트.
자료별로 읽는 법과 QS 데이터 형식은 `references/inputs.md`.

## 2. 비교형 쓰기

```bash
OUT="<저장 위치>/<제목>"
mkdir -p "$OUT" && cp "$SKILL/templates/shared.html" "$OUT/<제목>.html"
```

`{{…}}` 자리를 채운다. 문항과 답은 `<script>`의 `PEOPLE` · `GROUPS` · `QS`에 넣으면 렌더러가 그린다. 서술(요약 · 비교 · 제안)은 HTML에 직접 쓴다.

순서: 표지(한 문장 결론) → 요약(둘 나란히) → 문항별 답변(자동) → 비교 → 먼저 살펴볼 것 → 제안(확정 아님을 밝힘) → 함께 이야기할 것

- 독자는 응답자 본인일 수 있고, 슬랙에 올리면 누구나 볼 수 있다. **평가받거나 통보받는 느낌이 들지 않게** 쓴다. 합니다체, 강점식, 제안은 "…하면 어떨까요?"
- 섹션별로 쓰는 법, 쓰지 않는 표현, 바꿔 쓰는 표현은 `references/writing.md`
- 뼈대의 반복 블록(`<!-- … -->` 표시)은 예시가 하나씩만 들어 있다. 필요한 만큼 복제하고, 쓰지 않는 구성 요소는 지운다. 주석도 채운 뒤 지운다

## 3. 단일형 쓰기

```bash
mkdir -p "$OUT" && cp "$SKILL/templates/single.html" "$OUT/<제목>.html"
python3 "$SKILL/scripts/md_to_qs.py" "<질문 리스트.md>" > <임시 폴더>/qs.js
```

`qs.js`의 `const GROUPS` · `const QS`를 뼈대 `<script>`의 빈 두 줄 대신 붙이고, 나머지 `{{…}}`를 채운다. 문항은 `renderSolo`가 자료 순서 그대로 한 열로 그린다.

순서: 표지(한 문장 결론 + 현장 환경) → 요약(대상별로 따로) → 문항별 답변(자동, 전체) → 비교(같은 질문에 답이 갈린 곳만) → 먼저 살펴볼 것 → 제안 → 함께 이야기할 것

- 문항을 대상별로 다시 짝짓지 않는다. 자료의 섹션 순서가 곧 리포트의 문항 순서다
- 비교 카드는 같은 질문에 답이 갈린 곳만 만든다. 한 장도 없으면 비교 섹션을 통째로 지운다 (`references/writing.md` POL-06)
- 요약의 facts 라벨은 대상끼리 맞추지 않는다. 각 대상에 실제로 답이 있는 것만 쓴다
- 문장 규칙은 비교형과 같다. 섹션별 쓰는 법은 `references/writing.md`의 "단일형"

## 4. 템플릿은 그대로, 채운 사본에서 할 일

템플릿 파일(`templates/`)은 고치지 않는다. 디자인과 구조의 정본이다.
템플릿에는 이 스킬에서 쓰지 않는 자리가 남아 있다. 채운 사본에서 아래처럼 처리한다.

| 템플릿에 있는 것 | 채운 사본에서 |
|---|---|
| 제안 섹션의 3열 블록 `.roles` (`p1` · `p2` · `lead`) | 늘 지운다. 흐름부터 쓴다 |
| 인물 색 `p1` · `p2` · `lead` | `p1`은 첫째 응답 세트, `p2`는 둘째 응답 세트의 색이다. `lead`는 쓰지 않는다 |
| 고정 문구 "두 분", "두 분의 공통점" | 응답 세트가 사람이면 그대로 둔다. 학원 · 화면처럼 사람이 아니면 "두 학원"처럼 바꾼다 |
| `{{준비 섹션 이름}}` | "먼저 살펴볼 것" |
| `{{제안 섹션 이름}}` | "개선 방향 제안" |
| 현황 표 | 자료에 있는 사실(지금 쓰는 방식)로만 채울 수 있을 때만 둔다. 아니면 지운다 |

## 5. 조립과 검사

필수 (모든 화면)

```bash
python3 "$SKILL/scripts/assemble.py" "$OUT"/*.html
python3 "$SKILL/scripts/check_shared.py" "$OUT/<제목>.html"
```

- `assemble.py`: 공통 CSS(`report.css`)와 렌더러(`render.js`)를 파일 안에 넣어 하나로 만든다. 채우지 않은 `{{…}}`가 남았으면 알려 준다. 조립한 뒤 고쳤다면 다시 돌려 남은 자리를 확인한다
- `check_shared.py`: 평가 · 추정 표현을 찾는다. 금지 0건이 될 때까지 고치고, 반말 경고는 하나씩 읽고 판단한다
- 원문 대조: 단일형은 `md_to_qs.py`를 다시 돌려 리포트의 QS와 diff한다. 폼 · CSV는 자료의 답과 QS를 스크립트로 대조한다. 원문이 한 글자도 바뀌지 않았는지 확인한다

선택: 캡처 검증 (Code 탭이고 Chrome이 있을 때만)

```bash
python3 "$SKILL/scripts/shot.py" "$OUT/<제목>.html" <임시 폴더>/shot.png --hide ".hero"
```

- 섹션별 · 좁은 폭 스크린샷을 찍어 본다. 찍을 것과 문장 점검 목록은 `references/verify.md`
- 다른 화면이거나 Chrome이 없으면 캡처 검증을 건너뛰었다고 알린다. 대신 `references/verify.md`의 "볼 것" 목록을 주고, 사용자가 HTML을 열어 눈으로 확인하게 한다

## 6. PDF (요청할 때만)

```bash
python3 "$SKILL/scripts/to_pdf.py" "$OUT/<제목>.html"
```

- 브라우저와 한글 글꼴을 먼저 찾고, 있으면 리포트 옆에 `<제목>.pdf`를 만든다
- 종료 코드 3이면 이 화면에서는 PDF를 만들 수 없다. 스크립트가 낸 이유를 그대로 알리고, 아래 중에서 고르게 한다
  - HTML만 받는다
  - HTML을 자기 브라우저에서 열고 인쇄 › PDF로 저장한다. A4 인쇄 설정이 들어 있어 같은 모양으로 나온다
  - Code 탭에서 같은 요청을 다시 한다
- 인쇄 레이아웃 확인은 `references/verify.md`의 "PDF"

## 7. 전달

- 만든 파일 경로를 알린다. Chat에서는 내려받을 파일로 준다
- 아티팩트 게시는 사용자가 요청할 때만 한다. 처음에는 비공개라 Share 메뉴로 공유해야 다른 사람이 열 수 있다고 알린다
- 응답자에게 보내기 전에 0절의 동의 확인을 거쳤는지 다시 본다

## 늘 지킬 것

- **응답 원문은 손대지 않는다.** 맞춤법 · 띄어쓰기 · 말줄임까지 그대로. 응답자 본인이 읽는다
- **다른 질문의 답을 짝짓지 않는다.** 대결 카드는 같은 질문에 답이 갈린 곳만. 카드 수 기준보다 이것이 먼저다 (POL-06)
- **자료 밖의 정보를 결과처럼 쓰지 않는다.** 코드 상태, 작성자가 따로 아는 사실 등은 넣지 않거나 출처를 밝힌다
- **모르는 것은 채우지 않는다.** 자료에 없으면 "여쭤보지 못했습니다"로 남기고, 판단은 "함께 이야기할 것"의 질문으로 돌린다
- **대비와 강조는 비교 섹션 한 곳에만.** 문항 목록에는 배지를 넣지 않는다
- 대문자 라벨, 가운뎃점으로 이은 메타 문자열, 링크 뒤 `→`를 쓰지 않는다
- 번호는 흐름 · 우선순위 · 문항에만
- 네이티브 한국어. 영어 직역투를 피한다 (고친 예는 `references/writing.md`)
- 디자인 토큰과 구성 요소는 `templates/report.css`에 있다. 새 색 · 새 컴포넌트를 만들지 않는다. 60:30:10(흰색 · 연보라 · 진보라)이 깨진다
- 인증 정보(계정 · 비밀번호), 개인 연락처는 자료에 있어도 리포트에 넣지 않는다
