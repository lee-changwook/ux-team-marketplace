# artifact-style

UX팀이 만드는 아티팩트 · HTML 페이지에 팀 토큰, 컴포넌트, 글쓰기 규칙을 입힌다.
게시 전에 문장 줄바꿈 · 버전 라벨 · 토큰 밖 색값을 점검한다.

## 어디서 되는가

| 단계 | Chat | Cowork | Code 탭 |
|---|---|---|---|
| 토큰 · 컴포넌트 · 글쓰기 입히기 | 됨 | 됨 | 됨 |
| `scripts/preflight.py` 점검 | 실행 환경에서 됨 | 실행 환경에서 됨 | 됨 |
| 라이트 · 다크, 390px 캡처 확인 | 안 됨 → 사용자에게 확인 부탁 | 안 됨 → 사용자에게 확인 부탁 | Chrome이 있으면 됨 |

- 스크립트는 Python 표준 라이브러리만 쓴다. 명령을 실행할 수 없는 상황이면 `references/preflight.md`의 점검표를 손으로 본다.
- 캡처 확인을 못 하는 화면에서는 건너뛰었다고 알리고, 사용자에게 테마를 바꿔 보고 창을 좁혀 보라고 부탁한다.

## 이 스킬을 쓰지 않는 때

- 인터뷰 · 설문 · 현장 테스트 리포트는 `research-report`, 학원 사용자용 사용 설명서는 `feature-guide`가 만든다.
- 그 산출물은 각 스킬의 템플릿이 정본이므로 이 스킬의 토큰 · 컴포넌트를 입히지 않는다. 색이 팀 토큰과 달라도 고치지 않는다.
- 그 산출물을 아티팩트로 올릴 때는 글쓰기 규칙의 게시 부분(같은 링크에 다시 올리기, 버전 라벨 없음, Share로 공유)만 안내한다.
- Figma 시안은 `screen-to-hifi`가 맡는다.
- 레포 안의 제품 화면(티키타 프론트엔드 코드)에는 쓰지 않는다. 제품은 제품의 디자인 시스템을 따른다.

## 만드는 순서

1. **누가 보고 무엇을 정하는 문서인지** 한 줄로 확인한다. 요청에 없으면 묻는다. 이 한 줄이 머리의 제목과 리드가 된다.
2. **뼈대를 잡는다.** `references/components.md` 1절의 페이지 뼈대를 쓰고, `/* tokens.css */` 자리에 `references/_shared/tokens.css`를 처음부터 끝까지 그대로 붙인다.
   - 값을 골라 옮기거나 고치지 않는다. 다크 모드 구조와 기본 리셋이 그 안에 들어 있다.
3. **순서를 정한다.** 결론이 머리에 오고, 섹션은 판단할 것 → 확인할 것 → 참고 순서다. 해당하는 섹션만 둔다.
   - 회의 안건처럼 결론이 아직 없는 문서는 "무엇을 언제까지 정하는지"를 결론 자리에 둔다. 정하지 않은 것을 정한 것처럼 쓰지 않는다.
4. **컴포넌트를 고른다.** `references/components.md`에서 고른다. 없는 모양이 필요하면 카드 · 칩 · 범례를 조합해 새로 짠다.
5. **글을 쓴다.** `references/_shared/writing.md`를 따른다. 페이지에서는 아래 "페이지 글"을 함께 지킨다.
6. **함정을 본다.** `references/pitfalls.md` 7개를 한 번 훑는다.
7. **게시 전 점검을 한다.** 아래 "게시 전 점검"대로 한다.
8. **게시한다.** 아래 "게시"대로 한다.

## 색

- 색은 `var(--…)`만 쓴다. 토큰 블록 밖에 `#…` · `rgb(…)` · 이름 색(`white` 등)을 쓰지 않는다. SVG의 `fill` · `stroke`도 같다.
- 옅은 바탕은 토큰을 섞어 만든다: `color-mix(in srgb, var(--line-cw) 12%, var(--surface))`. 두 테마 모두 따라온다.
- 꼭 필요한 색이 토큰에 없으면 새 색값을 쓰지 말고, 리드에게 `shared/tokens.css`에 더하자고 제안한다. 그동안은 있는 토큰으로 만든다.
- 역할
  - `--accent` 강조(Magenta): 지금 보는 것, 초점, 꼭 봐야 할 한두 곳. 한 화면에 한두 곳만 쓴다.
  - `--warn` 경고: 끊김 · 빠짐 · 충돌. 점선 테두리와 글자 라벨을 함께 쓴다. 색만으로 경고하지 않는다.
  - `--line-cw` · `--line-yu` · `--line-ju`: 창욱 · 유진 · 주은을 표시할 때만 쓴다. 분류 색으로 쓰지 않는다.
  - 나머지(`--bg` · `--surface` · `--ink` · `--muted` · `--rule` · `--hatch`): 바탕 · 글자 · 선
- 결정 상태는 색이 아니라 모양으로 나눈다: 채움(합의) · 테두리(논의 중) · 점선(제안) · 옅은 회색 바탕(미결).

## 서체

- 본문은 `var(--font-body)`, 코드는 `var(--font-mono)`다. 서체 이름을 직접 쓰지 않는다.
- 먼저 Pretendard · D2Coding을 쓰고, 보는 사람 PC에 없으면 IBM Plex Sans KR · IBM Plex Mono로 보인다.
  - Pretendard · D2Coding은 Google Fonts에 없어 아티팩트에서 불러올 수 없다. 설치한 사람에게만 보인다.
  - IBM Plex 링크는 `components.md` 뼈대에 있다. 지우지 않는다.
- `var(--font-mono)`는 코드 · 경로 · 숫자 · ID에만 쓴다. 한글 라벨에 쓰면 글자 사이가 벌어져 보인다.

## 페이지 글

- 서술 문단은 문장마다 줄을 바꾼다. HTML에서는 문장 사이에 `<br>`을 둔다. 불릿(`<li>`)은 예외다.
- 제목과 본문은 다른 줄(다른 요소)에 둔다.
- 팀원에게 쓰는 글은 높임말이다. 사람이 확인하기 전에는 "확정"이라고 쓰지 않는다. 근거가 없는 칸은 `미결`이다.
- 자체 ID를 쓰면 문서 맨 앞에 범례를 둔다.
- 날짜는 요일만 쓰지 않고 날짜를 함께 쓴다 (예: 10/16(금)).
- 꼬리에 근거 링크와 관련 문서를 둔다.
- 티키타 정책 · 용어를 옮겨 적을 때는 `tikita-policy` 스킬로 찾아 근거를 밝힌다. 찾을 수 없으면 `미결`로 둔다.

## 게시 전 점검

1. 페이지를 파일로 저장하고 스킬 폴더에서 `python3 scripts/preflight.py <페이지.html>`을 돌린다.
   - 고칠 것(토큰 · 색값 · 버전): 0건이 될 때까지 고친다.
   - 확인할 것(줄바꿈 · 범례): 하나씩 보고 고칠지 판단한다. 숫자 목록처럼 문장이 아닌 것은 그대로 둔다.
2. `references/preflight.md`의 점검표에서 스크립트가 보지 않는 것(결론 위치, 높임말, 강조색 개수, 경고 라벨, mono 서체 등)을 본다.
3. 라이트 · 다크 두 테마와 390px 폭을 확인한다. Code 탭이면 `preflight.md` 3절의 캡처 방법을 쓴다.
4. 고친 내용과 남은 확인 항목을 사용자에게 짧게 알린다.

## 게시

- 버전 라벨을 붙이지 않는다. 제목 · 본문 · 파일 이름 모두 해당한다.
- 고칠 때는 같은 아티팩트를 고쳐 같은 링크에 다시 올린다. 새 링크를 만들지 않는다.
- 아티팩트는 처음에 비공개로 만들어진다. 팀원에게 보일 것이면 Share 메뉴로 공유하라고 안내한다.
- 핸즈오프용이면 넘기기 전에 `handoff-check`로 글과 아티팩트가 맞는지 볼 수 있다고 알린다.

## references를 언제 읽는가

| 파일 | 읽는 때 |
|---|---|
| `references/_shared/tokens.css` | 뼈대를 잡을 때. 통째로 붙인다 |
| `references/_shared/writing.md` | 글을 쓸 때 |
| `references/components.md` | 뼈대와 컴포넌트를 고를 때 |
| `references/pitfalls.md` | 레이아웃을 짤 때, 게시 전에 |
| `references/preflight.md` | 게시 전에. 스크립트 결과를 읽을 때, 캡처 확인을 할 때 |

`references/_shared/`는 저장소의 `shared/`에서 복사된 사본이다. 고치지 않는다.
