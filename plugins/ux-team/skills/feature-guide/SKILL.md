# 기능 사용 설명서 (feature-guide)

기능 **하나**를 처음 쓰는 사용자가 따라 할 수 있게 안내하는 PDF를 만든다.

## 어디서 되는가

**이 스킬은 Code 탭 전용이다.**
캡처를 가리고 번호를 얹는 단계와 PDF 쪽을 확인하는 단계가 macOS 전용 Swift 스크립트이고, PDF는 내 Mac의 Chrome으로 만들기 때문이다.
화면 판별은 `references/_shared/surfaces.md`를 따른다.

| 단계 | Chat | Cowork | Code 탭 |
|---|---|---|---|
| 화면 문구 · 동작 확인 (레포 코드) | 안 됨 | 안 됨 | 레포를 연 경우 |
| 원고 · 캡처 목록 쓰기 | 안 됨 (안내하고 멈춤) | 안 됨 (안내하고 멈춤) | 됨 |
| 캡처 가리기 · 번호 배지 (`annotate.swift`) | 안 됨 | 안 됨 | 됨 (Xcode 명령줄 도구 필요) |
| PDF 만들기 (`build_guide.py`) | 안 됨 | 안 됨 | 됨 (Chrome 필요) |
| 쪽 확인 (`render_pdf.swift`) | 안 됨 | 안 됨 | 됨 (Xcode 명령줄 도구 필요) |

### Chat · Cowork에서 불렸을 때

아래 글을 그대로 출력하고 멈춘다. 원고 초안만 먼저 쓰지 않는다 (코드나 실제 화면으로 확인하지 않은 원고가 되기 때문이다).

> 사용 설명서 PDF는 Claude 앱의 **Code 탭**에서 만들 수 있습니다.
> 캡처 속 이름 · 전화번호를 가리는 단계와 PDF를 만드는 단계가 내 Mac에서만 돌기 때문입니다.
>
> Code 탭에서 이렇게 시작해 주세요.
> - 캡처 파일을 한 폴더에 모아 두고, Code 탭에서 그 폴더(또는 티키타 레포 폴더)를 엽니다.
> - "○○ 기능 사용 설명서 만들어 줘"라고 말하고, 계획서가 있으면 함께 알려 줍니다.
>
> 지금 화면에서는 진행하지 않겠습니다.

## 기본

- **독자**: 원장님 · 행정팀 · 강사님. 개발 어휘 없이 높임말 안내문체(`~합니다`·`~하세요`)
- **예시**: `references/example/` — 가상 기능(보강 신청)의 계획서 · 캡처 목록 · 원고 · 가공 캡처 2장과 `원본/`(가공 전 캡처 · 가공 spec). 처음 쓸 때 `매뉴얼 원고.md`를 열어 톤과 문법을 맞춘다. 예시 내용을 실제 기능 설명에 옮겨 쓰지 않는다
- **명령 경로**: 아래 명령의 `<스킬 폴더>`는 이 SKILL.md가 있는 폴더다
- **임시 폴더**: 렌더 PNG · 컴파일한 실행 파일은 임시 폴더(scratchpad가 있으면 그곳, 없으면 매뉴얼 폴더 밖의 임시 폴더)에 둔다. 매뉴얼 폴더에 남기지 않는다

## 산출물 위치

```
<저장 폴더>/
├── <기능> 매뉴얼.pdf              ← 결과물
└── <기능> 매뉴얼/
    ├── 매뉴얼 원고.md              ← 원고 (정본)
    ├── 캡처 목록.md                ← 찍을 화면·파일 이름·배지 위치 + 가공 현황
    └── 00_….png · 01_….png …       ← 가공한 캡처 (원본은 사용자 폴더에 그대로)
```

저장 폴더는 argument로 받는다. 없으면 Code 탭의 현재 폴더를 제안하고 확인받는다.

## 절차

### 0. 실행 전 점검

- Chrome이 있는지 본다 (`/Applications/Google Chrome.app` 또는 Chromium). 없으면 PDF를 만들 수 없으니 Chrome 설치를 안내하고 멈춘다
- `xcode-select -p`로 Xcode 명령줄 도구(`swift`)가 있는지 본다. 없으면 캡처 가리기 · 배지 · 쪽 확인을 할 수 없으니, 터미널에서 `xcode-select --install`을 직접 실행해 설치하라고 안내하고 멈춘다
- ⛔ 가리기를 건너뛰고 PDF를 만들지 않는다. 설치는 사용자가 직접 한다

### 1. 내용 수집 — 코드가 정본

- 먼저 티키타 레포 폴더가 있는지 묻는다 (지금 연 폴더가 레포면 묻지 않는다)
- **레포가 있으면**: 계획서(요구사항 목록·화면 계획)로 범위를 잡고, **문구는 실제 코드에서 그대로** 가져온다: 컴포넌트 `labels.ts`, 확인 창(`confirm(...)`) 문구, 토스트 문구(`toastMessage.ts`), 안내 모달 상수
- **레포가 없으면**: 실제 화면 캡처에 보이는 문구를 정본으로 삼는다. 캡처로 확인할 수 없는 동작(언제 뜨는지 · 무엇이 남는지)은 원고에 쓰지 않고 `캡처 목록.md` 현황에 `미결`로 남긴다
- 동작 설명(언제 뜨는지·무엇이 남는지·어디로 가는지)은 코드나 실제 화면으로 확인한 것만 쓴다. 추측으로 쓰지 않는다
- **아직 없는 기능은 쓰지 않는다** (예: 권한 요청 버튼이 미구현이면 그 안내를 뺀다 — 브라우저 설정을 뒤지게 하는 안내는 실패율이 높다)
- 범위(어느 장을 넣을지)가 애매하면 장 후보를 보여 주고 고르게 한다

### 2. 원고 + 캡처 목록 → 레이아웃 PDF 먼저

- 원고 구성: 표지 요약(전체 화면 한 장 + ①~⑤ 한 줄씩 + 꼭 알아둘 콜아웃) → 처음 한 번 준비(있으면) → 기능 흐름 순 단계 쪽 → 이럴 땐 이렇게
- 단계 쪽 하나 = 캡처 1장 + 번호 설명 3~5개. 길면 쪽을 나눈다
- `캡처 목록.md`에 파일 이름 · 찍을 화면 · 배지 ①②… 위치를 적는다. **테스트 조직·가명 데이터로 찍게** 안내한다
- 캡처 없이 빌드하면 `캡처 없음: 파일명` 자리만 남는다 — 레이아웃 확인용으로 먼저 보여 준다

### 3. 캡처를 받으면 — 점검 → 가공

**점검 (전부 본다, Read로 한 장씩)**

- **시안인가 실제 화면인가.** Figma 시안은 구현과 다를 수 있다(검색칸·체크박스·버튼 유무). 원고와 어긋나면 실제 화면으로 바꾸거나 캡처를 빼고 글로만 둔다 — ⛔ 시안을 실제 화면인 척 쓰지 않는다
- **개인정보.** 실명 · 전화번호 · 실제 회선 번호 · 이메일 · 주소창/탭 제목의 학원 이름. 테스트 데이터처럼 보여도 확신이 없으면 가린다
- 원고와 다른 표기(예: 시각에 날짜가 있나 없나)는 원고를 양쪽에 맞는 말로 고친다

**가공 — `scripts/annotate.swift`**

```bash
swift "<스킬 폴더>/scripts/annotate.swift" <원본.png> <출력.png> <spec.json>
```

- spec 형식은 스크립트 첫머리 주석과 `references/example/원본/*.json`을 본다
- 가리기는 **가명으로 바꿔 쓰기**(fill + text)가 블러보다 자연스럽다. 가명 예: 김하나·박서준·이도윤·최지우 / 010-5530-2187 / 회선 070-1234-5678 / 번호 일부 가림 `010-6***-2***`. 문장 중간의 이름만 바꾸면 글자 폭이 달라 옆 글자와 겹치므로, 그 줄 전체를 덮고 원래 글자 크기에 맞춰 다시 쓴다
- 배지는 번호 설명과 같은 번호를, 가리키는 요소 **바로 옆 빈자리**에 둔다(글자 위에 얹지 않는다)
- 원본은 고치지 않는다. 가공본만 매뉴얼 폴더에 두고, 가리지 않은 원본 사본은 매뉴얼 폴더에서 지운다
- 결과 이미지를 Read로 열어 상자 테두리·배지 위치를 확인하고 좌표를 고친다
- 반복이 많으면 `swiftc -O annotate.swift -o <임시 폴더>/annotate`로 한 번 컴파일해 쓴다

### 4. 빌드 → 렌더해서 눈으로 확인

```bash
python3 "<스킬 폴더>/scripts/build_guide.py" "<매뉴얼 폴더>/매뉴얼 원고.md" -o "<저장 폴더>/<기능> 매뉴얼.pdf"
swift "<스킬 폴더>/scripts/render_pdf.swift" "<pdf>" <임시 폴더>
```

- `--assets <폴더>`: 캡처가 원고와 다른 폴더에 있을 때. `--keep-html`: 디자인 손볼 때
- `build_guide.py`는 macOS 기본 `python3`(3.9)에서도 돈다. 따로 설치할 것이 없다
- 렌더한 PNG를 `sips -Z 800`으로 줄여 Read로 확인한다. 특히
  - 표지 캡처가 커서 번호 설명이 다음 쪽으로 넘어가지 않았나 → `{w=58%}`처럼 폭을 줄인다
  - 거의 빈 쪽이 생기지 않았나, 캡처가 너무 작지 않나
- 완성 PDF 위치를 알려 주고, 파일을 보낼 수 있는 도구가 있으면 함께 보낸다. 남은 일(재캡처 필요한 화면, `미결` 동작 등)을 `캡처 목록.md` 끝 '현황'에 적는다

```markdown
1. **상태별로 보기** — `대기` · `승인` · `반려`를 누르면 그 상태의 신청만 나옵니다.
2. …

## 1단계 · 단계 이름

한 줄 도입.

![](01_일정정하기.png){side}

1. `버튼 이름`을 누릅니다.

## 이럴 땐 이렇게

### 질문 형태 제목(…해요)

답 문단 또는 불릿.
```

| 문법 | 결과 |
|---|---|
| 첫 `##` 앞 | 표지 쪽 본문 (로고 · kicker · 제목 · 날짜 · subtitle 아래) |
| `## 제목` | 새 쪽에서 시작하는 단계 (굵은 제목 + 검은 줄) |
| `### 제목` | 쪽 안 소제목 (파란 바) |
| `![캡션](파일.png)` | 가로 전체 캡처 · `{w=60%}` 폭 지정 · `{side}`/`{side=55%}` 왼쪽 캡처 + 바로 뒤 번호 목록을 오른쪽에 |
| `1. 설명` | 빨간 원 번호 설명 (캡처 배지와 같은 색 `#FF5226`) |
| `- 설명` · `> 콜아웃` | 불릿 · 회색 바탕 콜아웃 |
| `` `버튼 이름` `` · `**굵게**` | 화면 문구는 백틱 — 굵게 렌더된다 |

## 문체

- 화면에 있는 이름은 **백틱으로 그대로** (`전체 처리에서 열기`, `신청하기`)
- 개조식 금지, 한 번호 설명 = 한두 문장. 무엇을 누르면 → 무엇이 되는지
- '이럴 땐 이렇게'는 사용자가 실제로 물을 법한 질문형(`…안 떠요`, `…그대로예요`)으로, 정상 동작이면 **왜 그런지**까지
- 개발 어휘(API·BE·배포·캐시·R-ID·프로젝트 번호) 금지

## 하지 않는 것

- 캡처 합성·시안을 실제 화면으로 대체 — 실제 화면이 없으면 캡처를 빼고 글로만 둔다
- 개인정보가 보이는 캡처 사용
- 구현되지 않은 기능·동작 안내
- 사용자·고객에게 직접 발송 (PDF 생성까지)
- 브라우저를 직접 조작해 캡처하기 (사용자가 명시적으로 시킬 때만)
- 회차 단위 업데이트 안내(릴리스 노트 가공) — 이 스킬은 기능 하나만 맡는다. 회차 안내는 리드에게 요청한다
