# 트리거 지도

스킬 12개의 `description`을 한곳에서 함께 정한다.
자동으로 켜지는 스킬이 11개라서, 겹치는 말을 어느 스킬이 맡는지 여기서 먼저 정해야 한다.

- `description`은 이 문서가 정본이다. SKILL.md의 `description`은 이 표의 문구를 그대로 옮긴다.
- 고칠 때는 이 문서를 먼저 고치고(리드 확인), 그다음 SKILL.md에 옮긴다. `scripts/skills.py check`가 두 문구가 같은지 본다.
- 200자 이내로 쓴다. 무엇을 하는지, 사용자가 실제로 하는 말 2~3개, 맡지 않는 것 순서로 쓴다.

## description

| 스킬 | 켜짐 | description |
|---|---|---|
| `hello-ux-team` | 직접 | UX팀 플러그인을 설치한 뒤 처음 한 번, 그리고 리드가 팀 지침 갱신을 알렸을 때 실행한다. 팀 지침을 설치하거나 붙여 넣을 글을 주고, ClickUp·Slack 연결을 점검하고, 하네스 안내 문서 링크를 준다. |
| `tikita-policy` | 자동 | 티키타 정책 위키를 찾아 읽는 스킬이지만 지금은 준비 중이라 위키가 연결되지 않았다. 청구·수납·결제·출결·재원생·수강생 같은 용어나 '출결 관리' 같은 페이지 이름이 나오는 정책 질문에서 켜져, 정책을 지어내지 않고 미결로 남긴다. |
| `research-report` | 자동 | 인터뷰·설문·현장 테스트 메모를 팀에 공유할 리포트(HTML 또는 PDF)로 만든다. '인터뷰 정리해 줘', '설문 결과 리포트로', '현장 테스트 결과 정리'처럼 응답이나 관찰 기록을 정리해 달라고 할 때 쓴다. |
| `feature-guide` | 자동 | 새 기능 하나를 원장님·행정팀·강사님에게 안내하는 사용 설명서 PDF를 만든다. '사용 설명서 만들어 줘', '기능 매뉴얼', '학원 안내 PDF'를 요청할 때 쓴다. 화면 문구를 레포 코드에서 가져오므로 Code 탭에서 쓴다. |
| `artifact-style` | 자동 | 아티팩트나 HTML 페이지를 만들 때 UX팀 공용 토큰과 글쓰기 규칙(결론 먼저, 문장마다 줄바꿈, 버전 라벨 없음)을 입힌다. 리서치 리포트·사용 설명서처럼 전용 스킬이 있는 산출물은 그 스킬을 따른다. |
| `screen-to-hifi` | 자동 | staging 화면을 Figma로 캡처하고, 말로 준 개선 방향을 그 위에 hifi 제안(본편·제안부·설명)으로 얹는다. '이 화면 피그마로 떠 줘', '기존 화면에 시안 얹어 줘', 'hifi 제안 만들어 줘'를 요청할 때 쓴다. |
| `kickoff` | 자동 | 전사 미팅에서 배정된 프로젝트를 ClickUp 팀 스페이스에 상위 태스크로 등록한다. '프로젝트 배정됐어', '상위 태스크 만들어 줘', '킥오프 등록해 줘'라고 할 때 쓴다. 만들기 전에 초안을 보여 주고 확인받는다. |
| `ticket-create` | 자동 | 메모·이미지·파일로 ClickUp 오류·개선 티켓을 작성한다. '오류 티켓 만들어 줘', '개선사항 등록해 줘', '티켓 초안만 작성해 줘'에 쓴다. 새 티켓의 초안과 등록을 맡으며 기존 티켓 수정·댓글·프로젝트 등록은 맡지 않는다. |
| `decision-log` | 자동 | 기획 중 정해진 결정을 누가·언제·근거와 함께 ClickUp 중앙 컨텍스트에 남긴다. '이거 결정됐어', '결정 기록 남겨 줘', '정한 내용 정리해 둬'라고 할 때 쓴다. 남기기 전에 초안을 보여 주고 확인받는다. |
| `call-lead` | 자동 | 프로토타입을 만들다 막혔거나 데이터 구조가 불확실할 때 리드를 부른다. 내용은 ClickUp 상위 태스크 댓글에 쓰고 Slack에는 링크와 멘션만 보낸다. '창욱님 불러 줘', '막혔어', '리드한테 물어봐'에 쓴다. |
| `handoff-check` | 자동 | 기획을 개발로 넘기기 전에 글과 아티팩트·프로토타입이 일치하는지, 미결이 표시됐는지 점검한다. 미결이 0건이면 다시 본다. '넘기기 전에 확인해 줘', '핸즈오프 점검', '전달 전 체크'라고 할 때 쓴다. |
| `intent-check` | 자동 | staging에 올라간 화면을 기획 의도와 대조해 차이 목록을 만든다. 화면을 고치거나 데이터를 바꾸지 않고 차이만 적는다. 'staging 확인해 줘', '의도대로 구현됐는지 봐 줘', '최종 확인'이라고 할 때 쓴다. |

## 겹치는 말 정리

| 말 | 맡는 스킬 | 가르는 기준 |
|---|---|---|
| 리포트 · 정리해 줘 | `research-report` | 원자료가 인터뷰 · 설문 · 현장 관찰이면 이 스킬. 그 밖의 문서 정리는 스킬 없이 처리 |
| 아티팩트 · 페이지 · HTML | `artifact-style` | 리포트 · 설명서처럼 전용 스킬이 맡는 산출물은 그 스킬이 우선 |
| 설명서 · 매뉴얼 · PDF | `feature-guide` | 독자가 학원 사용자(원장님 · 행정팀 · 강사님)일 때. 팀 내부 문서는 해당 없음 |
| 확인 · 점검 · 체크 | `handoff-check` / `intent-check` | 대상이 글과 아티팩트(넘기기 전)면 `handoff-check`, staging 화면(구현 후)이면 `intent-check` |
| 정리해 둬 · 남겨 둬 | `decision-log` | 정해진 결정일 때만. 회의 내용 전체 요약은 해당 없음 |
| 막혔어 · 물어봐 | `call-lead` | 프로토타입 · 데이터 구조 질문일 때. 정책 질문은 먼저 `tikita-policy`로 찾아본 뒤 |
| 배정 · 프로젝트 등록 | `kickoff` | 새 상위 태스크를 만들 때만. 기존 태스크 수정은 해당 없음 |
| 오류 티켓 · 개선사항 등록 · 티켓 초안 | `ticket-create` | 새 오류·개선 티켓의 표준 초안과 등록. 프로젝트 상위 태스크는 `kickoff`, 정책 질문은 `tikita-policy`, 결정 기록은 `decision-log`. 기존 티켓 수정·댓글 작성은 해당 없음 |
| 피그마 · 시안 · hifi | `screen-to-hifi` | 기존 화면을 바탕으로 할 때. 백지에서 새로 그리는 시안은 해당 없음 |
| 정책 · 용어 · 화면 이름 | `tikita-policy` | 티키타 도메인일 때. 지금은 준비 중이라 미결로 남긴다 (DEC-20). 티링 정책은 아직 없음 (`tring-policy` 준비 중) |
