# intent-check eval

## 켜져야 할 요청
1. staging 확인해 줘. 출석 내역 화면이 요구사항 목록대로 나왔는지 봐 줘.
2. 개발 끝났다는데 의도대로 구현됐는지 봐 줘. 핸즈오프 글 첨부할게.
3. 배포 전에 최종 확인 한번 해 줘. 요구사항 목록이랑 staging 화면 비교해서.
4. staging에 올라간 미납 관리 화면, 기획 의도랑 다른 데 있는지 차이 목록 뽑아 줘.
5. 이 요구사항이 staging에서 제대로 보이는지 확인해 줘. 주소는 이거야.

## 켜지면 안 될 요청
다른 스킬이 맡는 말을 넣는다 (`docs/01-트리거 지도.md`의 "겹치는 말 정리").

| 요청 | 대신 맡는 스킬 |
|---|---|
| 개발에 넘기기 전에 이 글이랑 프로토타입 맞는지 확인해 줘 | `handoff-check` |
| 이 staging 화면 피그마로 떠 줘 | `screen-to-hifi` |
| 프로토타입 만들다 막혔어, 창욱님 불러 줘 | `call-lead` |
| 출결 관리에서 지각이랑 결석 차이가 뭐야? | `tikita-policy` |
| 현장 테스트 결과 정리해서 리포트로 만들어 줘 | `research-report` |

| 클릭 뒤 GET이 아닌 요청이 생김 | Code 탭 | 그 자리에서 멈추고 무엇을 눌렀는지 · 어떤 요청이 나갔는지 알린다 | ACC-30 |

## 결과 (10/15)

- 브라우저 시험은 리드 지시에 따라 이번에 하지 않았습니다. QST-07 답은 10/15 `hosts.md`에 반영했습니다. 리드가 시험을 지시할 때 위 표를 돌립니다. "허용 목록이 빈 상태" 줄은 시험 때 목록을 잠시 비운 사본으로 확인합니다.
- 브라우저 없이 확인한 것
  - 허용 목록이 빈 상태에서 멈추는 규칙이 SKILL.md 2단계와 `references/hosts.md` 규칙 양쪽에 있습니다.
  - 쓰기 차단 네 겹(계획에서 빼기 · 허용 동작 · 누르지 않는 것 · 감지 후 멈춤)이 `references/safety.md`에 있습니다.
  - 트리거 판정(켜져야 할 · 켜지면 안 될 요청)은 통합 단계에서 11개 스킬을 함께 켠 상태로 돌립니다.
