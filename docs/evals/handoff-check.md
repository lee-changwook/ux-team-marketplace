# handoff-check eval

## 켜져야 할 요청
1. 개발에 넘기기 전에 확인해 줘. 요구사항 목록이랑 프로토타입 HTML 첨부할게.
2. 핸즈오프 점검 부탁해. 아티팩트 링크랑 정책 글 줄게.
3. 창욱님한테 전달 전 체크 한번 해 줘.
4. 이 글이랑 프로토타입이 서로 맞는지, 미결 빠진 거 없는지 봐 줘. 이제 넘기려고.
5. world 브랜치 push 전에 요구사항 목록이랑 구현이 일치하는지 점검해 줘.

## 켜지면 안 될 요청
다른 스킬이 맡는 말을 넣는다 (`docs/01-트리거 지도.md`의 "겹치는 말 정리").

| 요청 | 대신 맡는 스킬 |
|---|---|
| staging에 올라간 화면이 의도대로 구현됐는지 봐 줘 | `intent-check` |
| 프로토타입 만들다 막혔어, 리드한테 물어봐 | `call-lead` |
| 이거 결정됐어, 결정 기록 남겨 줘 | `decision-log` |
| 인터뷰 정리해서 리포트로 만들어 줘 | `research-report` |
| 수납이랑 결제 차이를 정책 위키에서 찾아 줘 | `tikita-policy` |

## 결과 (10/15)

가상 입력을 임시 폴더에 만들어, 스킬 문서만 읽은 별도 에이전트(Opus)에게 사례마다 따로 실행시켰습니다.
정답은 에이전트에게 알려 주지 않았습니다.

| 확인 | 결과 | 근거 |
|---|---|---|
| 사례 A 대조표 (ACC-26) | 맞음 | 어긋남: REQ-01 기본 기간(3개월 ↔ 1개월) · 글에만: REQ-06 엑셀 다운로드 · 아티팩트에만: 인쇄 버튼 등 4개 · 확인 못 함: REQ-02 · 04 · 05 (조건 · 흐름). 심어 둔 차이를 모두 찾았습니다 |
| 사례 B 미결 0건 경고 (ACC-27) | 맞음 | 경고 문구가 그대로 맨 위에 나오고, 축별 다시 볼 후보가 나왔습니다. 범례의 `QST` 정의는 미결로 세지 않았습니다 |
| "확정" 없음 (ACC-28) | 맞음 | 두 출력 모두 "확정" · "통과" · "넘겨도 됩니다" 0건. 사례 B는 사용자가 넘겨도 될 것 같다고 해도 판정하지 않았습니다 |
| 원문 변경 없음 (ACC-29) | 맞음 | 실행 전후 입력 4개 파일 해시가 같습니다 |
| 링크 못 읽음 · Chat 브랜치 | 시험 안 함 | 실제 화면이 필요해 통합 단계에서 확인합니다 |

시험에서 고친 것
- 보이는 축은 같지만 동작을 못 본 항목(REQ-02 · 04 · 05)이 "일치"와 "확인 못 함" 양쪽에 세어져 건수가 겹쳤습니다.
- "일치 (보이는 축만)"으로 적고 두 건수가 겹칠 수 있다고 요약에 밝히도록 SKILL.md 4단계와 `references/output.md`를 고쳤습니다.

트리거 판정(켜져야 할 · 켜지면 안 될 요청)은 통합 단계에서 11개 스킬을 함께 켠 상태로 돌립니다.
